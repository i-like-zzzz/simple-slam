# Submap 重构计划

这份文档只回答一件事：

当前 `simple_slam` 的 `Submap2D` 能不能重构成接近 Cartographer 风格的成熟子图体系，以及应该怎么做。

结论先说：

- 可行
- 但不能把目标写成“直接做到和 Cartographer 一样”
- 更现实的目标是“先把架构和数据流做成同类形态，再逐步补细节和性能”

## 1. 当前 `Submap2D` 的真实状态

当前实现见：

- `include/simple_slam/mapping/submap_2d.hpp`
- `src/mapping/submap_2d.cpp`

它现在的特点是：

- 固定大小局部栅格
- 地图与 world 坐标轴对齐
- 子图中心由 `map_center_` 指定
- 每次关键帧插入时做一次 ray casting
- 内部只维护一个 log-odds 栅格
- 子图生命周期是“最多两个活动子图重叠”

这个实现已经足够跑通局部 SLAM，但它离 Cartographer 风格的子图还有明显差距。

## 2. 你真正想靠近的是什么

如果你说“想做成和 Cartographer 一样的 submap”，真正值得学习的不是某一个类名，而是这几件事：

1. 子图有明确的局部坐标系
2. 子图和全局位姿图解耦
3. 子图内部表达适合 scan matching
4. 活动子图和完成子图的生命周期清晰
5. 节点和子图之间的约束是后端一等公民
6. 子图可以被后端优化整体移动，而不是把每一帧点都重投一遍

如果这六点做到了，系统的形态就已经开始接近 Cartographer，而不是停留在“一个能插 ray 的栅格类”。

## 3. 当前版本和目标版本的关键差异

### 当前版本

- world 轴对齐栅格
- `origin_` 和 `map_center_` 语义部分重叠
- 子图朝向没有真正参与索引
- 子图只是一张局部 occupancy grid
- 位姿图还没有约束层

### 目标版本

- 子图拥有自己的局部坐标系 `submap local frame`
- world 点先变换到子图坐标系，再做网格索引
- 子图位姿由后端统一管理
- 子图内部至少要支持更适合匹配的概率栅格表达
- 节点-子图约束能够进入后端优化
- 完成子图可以作为回环检测对象

## 4. 这次重构不该做成什么样

不建议一上来就做下面这些事：

- 直接照抄 Cartographer 的全部类结构
- 把 scan matcher、submap、backend 一次性全部推翻重写
- 在还没有稳定约束结构之前就先做复杂回环检测
- 一上来就追求 branch-and-bound、多分辨率金字塔、线程池全齐

这条路线的典型结果是工程会失控，最后既不能运行，也没法持续验证。

## 5. 推荐的重构目标

建议把这次重构的目标定成下面四条：

1. 把子图从“world 轴对齐栅格”改成“带局部坐标系的子图”
2. 把子图管理从 `LocalSlamFrontend` 中拆出来
3. 把“节点插入了哪些子图”显式记录成约束数据
4. 为后端优化和回环检测预留稳定接口

只要这四条成立，后续无论你选 Ceres、g2o 还是自写优化器，系统都能继续往上长。

## 6. 推荐的新子图模型

建议把 `Submap2D` 重构成下面这种语义：

- `local_pose`
  子图在全局中的参考位姿，由后端可更新
- `local_frame`
  子图自己的局部坐标系
- `high_resolution_grid`
  主匹配/建图用概率栅格
- `low_resolution_grid`
  预留给粗匹配或多分辨率搜索
- `num_range_data`
  当前插入的关键帧数量
- `state`
  `kActive` / `kFinished`

这里最关键的变化是：

子图里的网格不再直接“铺在 world 上”，而是固定在子图自己的局部坐标系里。

于是索引流程会变成：

1. `point_world`
2. 通过 `T_submap_world^-1` 变成 `point_in_submap`
3. 再由 `point_in_submap` 计算栅格索引

这一步是当前实现和成熟子图实现最本质的区别。

## 7. 推荐拆分类

建议不要继续把所有逻辑压在 `LocalSlamFrontend` 里。

更合理的拆分是：

- `LidarOdomTracker2D`
  负责 scan-to-scan 里程计
- `Submap2D`
  负责子图内部概率栅格和插入
- `ActiveSubmapManager2D`
  负责创建/切换/完成活动子图
- `ConstraintBuilder2D`
  负责构建节点-子图约束
- `PoseGraph2D`
  负责节点、子图和约束容器
- `PoseGraphBackend`
  负责优化调度和回环入口

这样你的代码边界会清楚很多。

## 8. 推荐分阶段实现

### 阶段 1：只重构子图坐标系

目标：

- 去掉当前 `map_center_` 驱动 world 轴对齐索引的方式
- 改成“子图局部坐标系 + 子图位姿”
- 保持前端行为尽量不变

交付标准：

- 当前 bag 能继续跑
- `scan-to-submap` 结果不明显退化
- 活动子图生命周期不变

### 阶段 2：抽出活动子图管理器

目标：

- 把 `MaybeGrowActiveSubmaps()`、`InsertIntoActiveSubmaps()` 从前端拆出去
- 前端只负责产生局部结果
- 子图管理器负责创建、切换和完成子图

交付标准：

- `LocalSlamFrontend` 只保留前端感知逻辑
- `Submap2D` 与节点层的依赖更清晰

### 阶段 3：定义约束数据结构

目标：

- 增加 `Constraint2D`
- 记录节点到子图的相对位姿和权重
- 把当前“插入了哪些活动子图”变成显式数据

建议约束最少包含：

- `node_id`
- `submap_id`
- `relative_pose`
- `translation_weight`
- `rotation_weight`
- `tag`
  可区分 `intra_submap` 和 `loop_closure`

### 阶段 4：接后端优化

目标：

- 后端根据节点、子图、约束做位姿图优化
- 优化结果更新节点位姿和子图位姿
- 前端继续产出局部结果，后端异步收敛

### 阶段 5：接回环检测

目标：

- 只对完成子图做候选检索
- 先用简单几何或距离门限筛候选
- 再做 scan-to-submap 或 submap-to-submap 验证
- 通过后加入回环约束

## 9. 什么叫“接近 Cartographer 风格”

下面这些做到以后，就可以说你的系统在架构上已经开始接近 Cartographer：

- 前端局部跟踪和子图管理解耦
- 子图有自己的局部坐标系
- 子图位姿可被后端整体优化
- 节点-子图约束显式存在
- 活动子图和完成子图区分明确
- 回环是对完成子图做的，而不是直接硬改前端轨迹

但下面这些没有必要在第一轮就追求：

- 完整复刻 Cartographer 的所有概率栅格细节
- 完整复刻其约束搜索实现
- 完整复刻其线程模型

## 10. 工程建议

如果现在就开始重构，我建议优先级是：

1. 先改子图坐标系和数据结构
2. 再拆活动子图管理器
3. 再加约束结构
4. 再做后端优化
5. 最后做回环

不要反过来。

先把子图做对，后端和回环才有稳定地基。

## 11. 最后的判断

“把 `submap` 打造成和 Cartographer 一样最好的 submap”这个目标，表述太大，不适合直接作为这一轮开发目标。

但把它改成下面这个目标，是完全可行的：

“把 `simple_slam` 的 `Submap2D` 重构成具有局部坐标系、可支持位姿图优化和回环检测的成熟子图骨架，并在接口和数据流上接近 Cartographer 风格。”

这个目标既正确，也能落地。
